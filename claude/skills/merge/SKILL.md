# Merge

The ship skill stops before the merge on purpose ("merge only on the user's go"); this skill is that go. It merges one pull request, and only one that carries review evidence. "push and pr" and "push and open the pr" run steps 1 and 2 and stop before the merge, reporting the PR link.

1. Account first, before any write: read the folder's gh login from the `includeIf` block of `~/.gitconfig` (or `gh_accounts` in `~/.claude/local/machine.json`), run `gh auth status`, and `gh auth switch --user <login>` when the active account differs. Say which account is active.
2. Identify the PR: `gh pr view --json number,title,baseRefName,headRefName,state,url,mergeable,reviewDecision,statusCheckRollup` on the current branch. No PR yet: push the branch (through the ship skill's push step, never `git push --force`) and open one with a short body (the PR body rule of the global CLAUDE.md); on a client repository the push and the PR creation prompt, expect it. Then stop here when the user asked only for "push and pr".
3. Review evidence for the current head, in this order, stop at the first that holds: a `pr-review-findings.json` in the repository whose `base` is this branch's merge base, with every finding fixed or refuted in the conversation or the handoff, where any commit made after its `generated` time is a fix commit whose own diff was re-reviewed (`/code-review` on that delta) or is docs only; a `/code-review` or pr-review run on this diff in the current conversation with every finding fixed or refuted under the same fix-commit rule; a review comment on the PR from a reviewer or a bot on the current head with no open thread. An open finding or thread is a stop, not evidence. None of these: run the pr-review skill now and fix findings through the delegate skill's resume step before continuing. Never merge on "it looked fine". Print the evidence line (file, run or comment, with its timestamp) in the same reply as the merge command so the record shows what the merge rested on.
4. Gates: `gh pr checks` must be green or the project CLAUDE.md must name the check as optional; `mergeable` must not be CONFLICTING (rebase or merge the base first through the delegate skill when the conflict is in code, directly when it is a docs file). A pending required review from a human reviewer is a stop: say who is owed.
5. Merge method and branch deletion: the method the project CLAUDE.md names; otherwise the repository default (`gh repo view --json mergeCommitAllowed,squashMergeAllowed,rebaseMergeAllowed`), squash when all three are allowed. `--delete-branch` only when the project deletes merged branches or the repository has delete-on-merge enabled.
6. Stacked PRs, only when the head branch will be deleted: `gh pr list --base <this branch> --state open`. Any open PR that targets this branch is retargeted to this PR's base first (`gh pr edit <n> --base <base>`), otherwise GitHub closes it when the head branch goes. When the branch stays, touch no other PR. Then run `gh pr merge <n> --<method>` with or without `--delete-branch` per step 5. A client repository prompts; expect it.
7. Local follow-up: when the base branch is checked out in another worktree of this clone, do not touch it (another session may own it). When this worktree holds the merged branch, `git fetch` and report that the branch can be removed; never delete a local branch or worktree in this skill.
8. Report in four lines: PR number and merge commit, the review evidence used, the account used, what is left (retargeted PRs, local branch cleanup, deploy if the project CLAUDE.md has a deploy section, which the ship skill owns).
